How I Work

Most projects start with a messy question, so the first thing I do is pin down a few answers:

  • What are we really trying to understand?
  • What decision will this support?
  • What data can we trust?
  • What should be automated, modeled, or generated, and what should stay with a person?
  • How will we know it’s working?

From there I work through it step by step: define the problem, shape the data, build a prototype, check the output, harden it, and write enough down that other people can trust it and use it without me.

I’m comfortable at both ends of that process. I can present to a leadership review in the morning and debug a pipeline in the afternoon.

LLM Judge Trustworthiness — Meta-Evaluation

Sole researcherLLM evaluation researchAnalysis plan published, results pending

A pre-registered study of how far you can trust an LLM judge to score grounded-generation quality, and which of its biases are big enough to flip a ranking. I published the full analysis plan before collecting any results. It includes two questions I haven’t resolved yet and a contamination check that runs before the main experiment, so it can’t end up as a footnote in the limitations section.

Highlights

  • A pre-registered decision rule for a data-contamination check, fixed before the check ran.
  • Blind pairwise human labeling with a hidden repeat subset for measuring intra-rater agreement.
  • A documented decisions log recording what changed in the design, why, and what prompted it.
  • An explicit power analysis stating which planned comparisons are adequately powered and which are descriptive only, decided before labeling begins.

Why it matters

Teams increasingly use LLM judges as a cheap stand-in for human review. But “mostly agrees with humans on average” and “safe to trust on the comparisons that matter” are different claims. This project is set up to test the second one directly.
